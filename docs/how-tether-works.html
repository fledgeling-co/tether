How Tether works

Tether connects a phone, tablet, desktop or browser app to services on a paired Mac or PC. The computer keeps the data and decides what each device may use. The connection is end-to-end encrypted whichever route carries it, and the person chooses the route.

Roles

Who holds what

Three kinds of participant take part. The host is the Mac or PC that runs the app's real work. A host app such as Fullframe or SimDeck runs the tether host process beside it and talks to it through that process's standard input and output, which only the host app holds. The clients are the companion apps on phones, tablets, other computers and browsers. The relay is an optional cloud forwarder for when the two are not on the same private network.

Only the host process holds the host's private key and the list of paired devices, and only it decides which services a device may open. Each service it can reach is a fixed loopback address set by the app's owner, so no client can name a destination. The relay joins encrypted streams and never sees a key, a pairing code or plaintext.

Routes

Chosen, never guessed

A route is either a private address (home Wi-Fi, a VPN or Tailscale) or an explicit cloud relay. Switching between them is always the person's choice. A private route that stops answering never falls back to the relay.

Relay

Forwards ciphertext

The host dials out to the relay over WSS and proves an app-scoped Ed25519 registration key. Each client connection gets a single-use ticket. Production relays admit only listed host IDs, and every connection, frame and stream is bounded.

Existing TLS apps

Ingress without decryption

An app that already speaks TLS 1.3 can send its own TLS through the same carrier. The optional ingress routes by the public server name and never terminates that TLS.

Implementation

The shared core

Every rule that decides trust, and every word on a Tether screen, is written once in Rust. tether-core holds the cryptography and owns no sockets. tether-model turns pairing into state machines that tell each platform what to send, what to show and what to save. It also holds the copy for every screen, the nearby record format and the Tailscale address rules.

Each kit drives those state machines through one JSON command interface. Apple and Windows call it as a C function, tether_call; Android reaches it through JNI, and browsers through WebAssembly. The host process and the command-line tool are Rust programs built on the same crates.

Trust

Pairing

Each app has its own identity on each device: an X25519 key that is never shared between apps and never leaves the device's protected storage. Pairing exchanges those keys and records which services the device may use. Every connection afterwards checks them. There are two ways to pair, and both end the same way. The client saves a pending record first, the host commits the device durably, and only the host's final reply makes the pairing usable.

Nearby, with a code on both screens

Finding each other

Hosts announce _tether._tcp with the app ID, a display name and the addresses to try. An announcement is only a hint; the code decides trust.

Approving

A code must be on screen for at least a second before an approval counts, and both owners have a minute to approve. The phone can also be invited from the computer's side.

Safeguards

The host holds two requests at once and starts at most twelve exchanges every ten minutes. Three declines pause a device for ten minutes, and three exchanges abandoned halfway turn nearby pairing off until the owner turns it back on.

With a typed code

The code

Eight characters from an alphabet without I, L, O or U. It lasts five minutes, allows three online attempts and works once.

Invitation links

A tether://pair link carries the route and the code together for a short time, so scanning or tapping it can stand in for typing.

Interrupted pairing

If the host's final reply never arrives, the client keeps a pending record it can recover or discard. A pending record cannot open any service.

Every later connection

Pinned, then granted

Every connection is a fresh Noise XX handshake. The host's key arrives in the second message, and the client compares it with the key it saved at pairing before sending the third message, which reveals its own key. A host at the right address with the wrong key therefore learns nothing about this device, and a connection error never replaces saved trust.

Limits

  • 16 KiB of plaintext per record, 4 KiB per control message
  • 8 data streams and 24 sessions at a time per host
  • 256 paired devices per host

Media

On a private route, media.open hands out a short QUIC lease. The certificate pin and a single-use token arrive inside the Noise channel. The lease ends with its session, after five seconds without a heartbeat, or on revocation.

Removing a device

The host's owner can revoke a device at any time, which also ends forwarding already under way. A device can also leave on its own; the host commits that removal before it acknowledges it.

Lifecycle

Connection states

Saved trust is not the same as being connected. A saved host reads Offline until a fresh, authenticated status reply arrives, and the kits check again every fifteen seconds while it is shown. A failed check retries after one, two and four seconds before going back to Offline.

Planned

Reaching a host away from home

Planned work; not part of this preview

Bonjour does not cross Tailscale, so a phone paired at home goes offline once it leaves the Wi-Fi, even when both devices are on the same tailnet. A planned change would have the host report its own Tailscale addresses to paired devices over the encrypted channel. A client would try them after its saved address, and the pinned key would decide which answer is the paired host.

What the host reports

A planned request, host.routes, would be answered only to paired devices. An address would count as Tailscale's only when its interface also holds a Tailscale IPv6 address, so a look-alike address from an internet provider is never reported.

Finding computers from a desktop

On a Mac, PC or Linux machine, the nearby list would add tailnet devices whose app port answers, named with their owner when they belong to someone else. It would read Tailscale's own installed program and refuse any copy it could not trust.

Phones and tablets

They cannot list tailnet devices without a Tailscale API key, so they would pair once nearby. After that they would reconnect through the reported addresses from anywhere, and the status would read "Connected through Tailscale".

Boundaries

What Tether does not do

  • It is not a hosted relay service. A deployment runs its own relay, and the operator can still deny service and see connection metadata.
  • It keeps no cloud copy of the host's data. The host must be awake and online for a client to use it.
  • It does not protect a device or computer that is already compromised. Plaintext and keys are in the app's memory while it runs.
  • It does not replace an app's own permissions. Screen control, repository access or account sharing remain the host app's decisions.
  • Tests and model reviews are not an independent cryptographic audit, and none has been done yet.
